Esta alternativa prepara un único acceso temporal para habilitar `krow_pilot_runtime` sin cambiar la contraseña de `postgres`. Preparar los archivos no despliega ni conecta a Supabase. El rol debe existir como NOLOGIN, sin poderes administrativos, con conexión limitada a 12 y solamente la pertenencia INHERIT a `krow_pilot_service`, sin ADMIN ni SET.

1. Ejecutar `node scripts/provision-pilot-edge/prepare.mjs`. El programa lee internamente la CA pública verificada y `SUPABASE_URL` de `apps/api/.env`; rechaza una URL de runtime ya configurada y cualquier preparación anterior. Guarda token aleatorio de 256 bits y verificador SCRAM en `.temp/pilot-provision/edge-request.json`, y la credencial de recuperación en `runtime.env`. Todos permanecen ignorados por Git, Docker y Railway. En Windows los archivos heredan los permisos de la carpeta privada del usuario.
2. Revisar y desplegar exclusivamente `edge-source/index.ts`, `metadata.ts` y `deno.json` de esa carpeta, con el nombre fijo `krow-pilot-private-bootstrap` y `verify_jwt=false`. Esos tres archivos contienen solamente CA pública, huellas SHA-256 y una caducidad absoluta de 10 minutos. El cuerpo autentica el bearer privado; desactivar la comprobación JWT de la plataforma es necesario para este token opaco. No cargar `edge-request.json`, `runtime.env` ni otros archivos privados al conector.
3. Ejecutar `node scripts/provision-pilot-edge/invoke.mjs --preflight`. Devuelve únicamente códigos sanitizados; comprueba identidad `postgres`, CREATEROLE, ADMIN sobre el rol preparado, TLS y permisos mediante metadatos. La existencia documentada de `SUPABASE_DB_URL` no garantiza su identidad o permisos reales. Si no se cumplen, se detiene sin cambiar ningún rol.
4. Tras revisar un resultado READY, ejecutar `node scripts/provision-pilot-edge/invoke.mjs --provision`. Envía por HTTPS el único verificador esperado. Una transacción serializada comprueba NOLOGIN y los permisos, establece PASSWORD y LOGIN, y rechaza repeticiones después del primer commit. La contraseña generada no se envía a esta función; permanece en el archivo privado de recuperación para verificar y configurar la API. La recuperación ya está guardada antes de invocar.
5. Reemplazar inmediatamente la función con `retired.ts`, sin dependencias, y comprobar que responde HTTP 410. El conector instalado permite redesplegar; no tiene herramienta de eliminación. La caducidad y la condición NOLOGIN protegen también ante versiones anteriores todavía en vuelo.
6. Ejecutar `node scripts/provision-pilot-password.mjs --recover`. Este modo no lee la contraseña administrativa ni cambia la base: verifica la conexión y permisos del runtime y solamente entonces actualiza `apps/api/.env`. Publicar únicamente las variables del runtime en el gestor de secretos del alojamiento.

Una respuesta incierta después de provisionar no justifica volver a preparar o rotar. Retirar la función y probar `--recover`: si el commit ocurrió, la credencial guardada es válida; si falló la autenticación, revisar el estado del rol antes de actuar. La preparación conserva los archivos parciales para revisión. No imprimirlos ni copiarlos al chat. No borrar un `provision.lock` sin confirmar que el proceso anterior terminó. Si caducó antes de provisionar, revisar que el rol siga NOLOGIN antes de retirar los archivos temporales concretos y preparar de nuevo.

TLS usa siempre `aws-1-us-east-1.pooler.supabase.com:5432`, con validación de CA y nombre del servidor; nunca vuelve a texto plano. La CA tiene huella DER SHA-256 `807025AD50D4ED219D2C9C7D299C004F824EB00CF7F65AFEF607D07B72E6CAFA`. La función solo acepta la contraseña interna de una URL integrada cuyo usuario sea `postgres` (o `postgres.yyjbqzsokxpzhevpanyq`), y verifica después la identidad real. No devuelve ni almacena la URL integrada. No acepta SQL, roles o conexiones arbitrarios.

La CA suministrada amplía las raíces de confianza de Deno; su huella no significa que se excluyan todas las demás raíces del sistema. Después de conectar, `client.session.tls` debe ser true y el transporte TCP: comprueba directamente Edge→pooler. `pg_stat_ssl` describe la conexión interna del pooler a PostgreSQL, por lo que no permite inferir el TLS del cliente externo. Los controles de permisos rechazan CREATE sobre esquemas/base y exigen los permisos necesarios, pero no son una lista exhaustiva de permisos: revisar por separado los grants adicionales de `krow_pilot_service` y de `PUBLIC`, especialmente ejecución de funciones y acceso `pg_net`, antes de habilitar LOGIN.

No hay tokens, contraseñas ni verificadores en el código enviado a MCP o en migraciones. El verificador seguirá en el catálogo PostgreSQL como material de autenticación; la configuración de logs, auditoría y errores del servidor puede retener el ALTER ROLE. No se promete su ausencia de todos los logs de la plataforma. El código no registra cuerpos, cabeceras, SQL, avisos ni errores originales.
